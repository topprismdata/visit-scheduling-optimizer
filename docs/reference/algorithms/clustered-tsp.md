# 0. 30 秒理解

Clustered TSP 曾尝试解决的问题：

> 如果业务希望销售人员尽量连续拜访同一区块门店，是否可以把“区块连续性”直接编译进
> TSP 目标？

原方法：

    区域信息

    ↓

    修改距离矩阵

    ↓

    TSP 求解

    ↓

    产生区块连续路线

核心思想：

> 用大罚项把软区块偏好转化为路线成本。

# 2. 方法机制

核心：

跨区边增加罚项：

\[ D’(i,j)=D(i,j)+M \]

其中：

    zone(i) != zone(j)

时：

    M = 10 × max(D)

实现：

``` text
同区移动：

真实距离


跨区移动：

真实距离 + 大罚项
```

目标：

让求解器倾向：

    A区店

    连续访问

    ↓

    B区店

------------------------------------------------------------------------

# 3. 为什么这个方法有吸引力

业务直觉：

销售人员跨区域移动可能带来：

- 路网绕行；
- 管理复杂度；
- 区域切换成本。

因此：

希望：

    一个时间段集中一个区域

类似：

    cluster first
    route second

------------------------------------------------------------------------

# 4. 本项目评估结论

结论：

> 本场景否决，不进入生产矩阵。

原因：

------------------------------------------------------------------------

## 4.1 KM 净收益为负

真实路网测试发现：

    聚类带来的绕行成本

    >

    减少跨区穿行收益

因此：

总公里数恶化。

------------------------------------------------------------------------

## 4.2 论文结果不可直接迁移

论文中：

    +3.5%

改善来自：

    Amazon last-mile 密集城市场景

而当前场景：

- FMCG 门店分布；
- 行政区形态；
- 路网结构；

不同。

因此：

不能外推。

------------------------------------------------------------------------

## 4.3 与 R2′ 走廊语义存在冲突

R2′关注：

    合同节奏

    +

    可执行拜访走廊

Clustered TSP 强制：

    行政/区块连续

可能导致：

- 挤压每日走廊；
- 增加不自然绕行；
- 破坏业务路线结构。

------------------------------------------------------------------------

# 5. 为什么不是算法错误

需要区分：

    方法正确性

    ≠

    业务适配性

该方法：

数学思想成立。

问题：

目标函数中的：

    zone continuity

不是当前业务真正成本。
