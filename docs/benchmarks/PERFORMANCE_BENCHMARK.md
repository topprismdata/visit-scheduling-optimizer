## 0. 四个核心问题的直接回答

**Q1：后续调整是否真的以上一次 V3 结果为起点增量优化？**  
**部分成立，且未接入生产流程。** 证据：
- `alns_v3.py` 的 `solve()` 签名是 `(data, D, time_budget, zone_of, seed)` ——**没有起点参数**，每次都从 `data.days_orig`（原始 SRP 计划）重新初始化（alns_v3.py:67）。V3 的 Tour-Carrying 只在单次 solve() 进程内生效，**不能跨运行复用**；
- `mo_alns_v4.py`（V4）有 `base=` 参数，实测确认以 V3 结果为基准（场景 B 起点里程恒为 263.2 = V3 当日水平）；
- 但 V4 目前**只存在于研究脚本** `run_mo_v4.py` 和本次 bench，**没有出现在 `runner.py` 的任何模式里**（runner MODES 无 mo_alns_v4）。所以"生产入口的第一次规划 → 保存 V3 结果 → V4 以它为基准"这条链路是**手工拼接**的，不是自动流程。

**Q2：V3、V4、rolling-horizon 各自负责什么？**  
- **V3（alns_v3）**：首次完整月度规划的唯一生产求解器（runner deep/standard 不含它——严格说它也不在 runner MODES 里，只在 `run_v3_all.py`/`run_all_lines.py` 研究脚本中）。**不具备微调能力**（无起点参数）。  
- **V4（mo_alns_v4）**：以任意给定解为基准（`base=`）的三目标帕累托前沿生成器（里程/相对基准改动量/CV）。**这是当前唯一能做"以上次规划为起点的再优化"的模块**，但未接入 runner。  
- **rolling_horizon / lock_replan（pvrp_cg 冻结目录）**：**纯框架代码，零求解器接线**。实测 grep 全仓库：`rolling_replan`/`incremental_replan` 的调用方只有彼此（定义文件自身），无任何生产/研究脚本引用；`rolling_replan()` 只返回 `{"status","locked_count","unresolved_count",...}` 元数据字典，不产出任何计划。**它目前只完成了锁定与任务拆分，未完成增量重规划**。

**Q3：微调是否只重算受影响门店和日期，还是重新初始化整条线路？**  
- **V3 短预算 = 整线重初始化**（铁证，B-finetune-V3control）：30s 预算重跑 V3，iters=31,868、起点里程与全量首次规划同源（265.1 km），它**看不见**上次结果，只能从零再收敛一遍；  
- **V4 = 真增量**：以 base（v3 或扰动后 v3）为唯一种群源头，每代算子只动 1–2 家店、只重算被触碰日的 2-opt（O(n) 插入 + 局部两日 polish）。实测 K=1 时最终解只偏离 base 3 个日期（"perturbed 1 stores, affected_days=3"）。  
- 但两个诚实保留：①V4 的全局目标 `total_km` 每代仍对全部日求和（O(总边数) 评估，非 O(1) 增量账本）；②**墙钟时间不随 K 缩小**——K=1 和 K=16 都是 30.0s，因为它是"预算驱动"不是"收敛驱动"（见 §2-B）。

**Q4：三类操作各需多长时间？**（M2 实测，缓存命中）

| 操作 | 实测墙钟 | 说明 |
|---|---|---|
| **首次完整规划**（09 线，推荐流程 nn2opt+CP-SAT+V3@300s） | **303 s ≈ 5.1 分钟/线** | 其中 V3 占 300s 且**全部撞满预算**；nn2opt 0.01s + CP-SAT 3.0s + 校验 ≈3s |
| 首次完整规划（V3@60s 预算档，10 线平均） | **60.0 s/线** | 10/10 线 60.01–60.03s；里程与 300s 生产档差 −7.2~+24 km（见 D 表） |
| **月度微调**（V4，改 1/3/5/16 家店） | **= 你给的预算**（30s 预算→30.01–30.02s） | 不会自动提前结束；预算设 5–10s 即可在 5–10s 内拿到与 30s 基本同水平的解（待专项标定） |
| **当天临时插单**（走廊投影工具） | **75–330 μs**（微秒级） | K=1/3/5 中位 200μs；真实 7/1 全月最大样本 K=13：327μs |

### 遗留缺陷与建议（按优先级）
1. **V4 未进 runner**：`base=v3` 手工接线应固化为 `--mode refine`（V3 结果自动持久化 → V4 基准）；

## 9. 数据质量缺陷：Haversine 回退缓存污染（2026-09-04 核查）

**现象**：`run_all_reps_actual_vs_agent.py` 在 FOSSGIS 429 限流时回退 `1.41×Haversine 校准矩阵`并**持久化**为 `data/cache/dist_{line}_{date}_{n}.npy`。全量检测 250 个日级矩阵：**124 个（约半数）为回退产物**（特征：距离值恒为 3 位小数规则网格；OSRM 实测值位数不规则）。
