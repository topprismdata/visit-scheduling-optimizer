## 1. 背景与目标

不同客户的门店布局、规模、合同组合及响应时间要求不同。矩阵用于识别算法的适用条件，支持后续按场景选择引擎。它不预设某个算法获胜，也不以某次真实线路结果否定一种机制。

现有生产矩阵包含基线保底、R2 热启动的 B&P 组合及重复排序列。它可以评价生产流水线，但直接用于独立算法比较时难以判断收益属于谁。新研究协议与生产协议并存，分别回答各自的问题。

### 1.1 Goals

| 目标 | 判定标准 |
|---|---|
| 干净 | 独立格不读取其他格的算法输出；共同输入及初始化规则明示 |
| 清晰 | 每一行有明确算法身份，每次对照明确固定项和变化项 |
| 公平 | 同组实例、约束、距离、评估口径一致；预算方式与实际开销完整记录 |
| 可归因 | 区分算法直接产物、统一 SP 重组收益、组合算法增量 |
| 可复核 | 版本、配置、输入、随机种子、路线与状态可追溯 |

### 1.2 Non-Goals

- 不生成一个覆盖所有场景的总冠军分数。
- 不在本设计内重写搜索器或开发新的精确定价器。
- 不把静态月历实验解释为动态插单能力；动态事件回放另设扩展协议。
- 不将真实与合成结果混算，不回写历史生产矩阵结果。

### 1.3 成功标准

先通过协议守卫和小实例验证，再完成冻结清单上的运行。报告能回答：同条件下谁得到什么质量、花多少时间、是否合法、改善来自何处。适用域结论先作为探索性假设，经过独立留出实例验证后才进入运行路由规则。

## 2. 矩阵总览：三类对照，各自控制变量

| 对照 | 行 | 列/变化因素 | 固定项 | 回答的问题 |
|---|---|---|---|---|
| A 日历算法矩阵 | 原分配基准及各独立日历引擎 | 实例 × 预算档 | 最终路线排序规则、Contract-SP、业务约束 | 谁更会选择每天拜访哪些店？ |
| B 路线算法矩阵 | NN+2-opt、多起点 NN+2-opt、CP-SAT、LKH-3 | 固定日店集 × 路线预算档 | 完全相同的门店集合与距离矩阵 | 对同一批店，谁排得更好、更快？ |
| C 组合增量矩阵 | R2、B&P 独立对照、R2→B&P 组合 | 同一输入 × 显式分段预算 | 相同评估流程 | 组合比单独运行多带来多少收益，代价是什么？ |

A、B、C 是互补实验，不把“日历算法×路线算法×所有预算×所有实例”一次全展开。需要验证端到端交互时，再选取少量明确的 A×B 组合；此时结论必须标注为流水线效果。

## 3. 行定义：算法身份与产物边界

### 3.1 A：日历算法矩阵

| 展示名称 | 实现标识 | 身份 | 允许的输入与初始化 | 交付产物 |
|---|---|---|---|---|
| 原分配基准 | `base` | 不改变门店→日期分配 | 共同原始计划 | 原分配日历，按共同规则排序 |
| 合同整店局部搜索 | `r2_alns` | 合同合法的整店星期几搜索 | 共同原始计划，自身搜索 | 直接日历与自身候选列 |
| 路径反馈大邻域搜索 | `alns_v3` | 路径反馈 ALNS | 共同原始计划，自身搜索 | 直接日历与自身候选列 |
| 路径反馈混合遗传搜索 | `hgs_pvrp` | 种群与路径反馈 HGS | 共同原始计划，自身搜索 | 直接日历与自身候选列 |
| 对偶驱动列生成 | `sp_cg` | LP 对偶引导定价供列 | 共同原始计划生成的起始列，自身定价 | 候选列、受限主问题诊断 |
| 独立分支定价 | `bp_solo` | 节点 LP、分支、定价框架 | 共同原始计划、自带热启动与搜索 | incumbent、自身候选列、证明诊断 |

`base` 是参照，不作为搜索算法排名。同族内部参数变体另做消融；ALNS 与 HGS 等不同机制保留独立行。现有实现若不能通过合同闸，应如实记录，其生产就绪程度与算法机制的潜在价值分别解释。

**禁止隐藏组合**：`bp_solo` 不调用 R2，不接收 R2 日历或池。公共数学工具、估计器代码与原始数据可以共享；某次运行生成的日历、候选列、对偶或 incumbent 不可以隐式共享。

### 3.2 B：路线算法矩阵

| 展示名称 | 实现标识 | 产物口径 |
|---|---|---|
| 最近邻与 2-opt | `nn2opt` | 启发式路线 |
| 多起点最近邻与 2-opt | `multistart_nn2opt` | 明确起点清单/数量的启发式路线 |
| 约束规划开放链求解 | `cpsat` | 路线及 OPTIMAL/FEASIBLE 等求解状态 |
| LKH-3 开放非对称路线求解 | `lkh3` | 启发式路线及真实执行/回退状态 |

不预设这四行具有固定的质量或速度顺序。多起点不称为“精确算法”；CP-SAT 仅在有效求解状态支持时称为日内已证最优。缺少可执行依赖时记录 UNAVAILABLE，不用替代算法冒充该行。

### 3.3 C：组合格

首期仅登记 `r2+bp`：R2 供日历/列，B&P 接收这些明确产物再运行。记录父 R2 run ID、输入列哈希与两段预算。其他组合如需加入，必须先登记名称和依赖关系。

## 4. 所有格共同遵守的条件（Invariants）

| 项目 | 共同规则 |
|---|---|
| 实例 | 同组比较使用相同 instance_id、输入哈希、门店索引与日历 |
| 距离 | 同一 OSM 骑行路网矩阵，保留方向性、单位与路网来源；不使用直线替代 |
| 日内目标 | 开放、无场站的单日路线长度；直接按矩阵逐边重算 |
| 业务约束 | 合同/相位、星期几一致性、派生拜访次数、完整日期及双向容量走廊一致 |
| 初始计划 | 共同输入的同一个已验证合法计划；不把独立引擎使用它初始化视为污染 |
| 失败处理 | 不因某格失败而追加外部基线列；失败保留为结果 |
| 评价 | 相同验证器、数值单位与容差；不通过业务闸的结果不能作为质量改善 |
| 实验环境 | 同组固定机器、依赖版本、线程配额及缓存策略；记录实际配置 |

**独立性是来源隔离，不是内容互斥。** 两个引擎独立找到同一日店集或路线应被允许；生产编排额外注入的保底列与引擎自身初始化必须分开记录。

对于同成本、相同约束、无删列且主问题精确求解的情况，池包含关系只能推出最优目标不劣，不能推出目标必然相等。

## 5. A 矩阵的统一流水线与贡献拆分

```text
共同实例与合法初始计划
        ↓
各引擎独立生成：直接日历 / incumbent / 候选列
        ↓
走廊过滤 + 同日店集归并 + 共同路线排序
        ↓
只用本格池运行同一 Contract-SP
        ↓
独立业务复验 + 距离重算 + 统一记分卡
```

### 5.1 两个结果都保留

- `native_result`：引擎直接交付的日历/incumbent；同时保存内部成本与按共同排序规则评价的成本。无直接可行日历时留空。
- `pipeline_result`：本格候选池经过共同排序和 Contract-SP 后的最终结果。

A 的主比较对象明确标为“引擎＋共同 Contract-SP 流水线”。不能把 SP 重组收益全部称为引擎直接搜索收益。原分配经 CP-SAT 且各日证完时作为基线 A；未证完时标为限时参照，禁止称为已证最优基线。

若引擎提供有效直接日历，其列须进入自身候选池，便于评价 SP 重组收益。SP 达到 OPTIMAL 且使用同一列成本时，应不劣于池内直接日历；限时 FEASIBLE 不作此保证。失败不能以临时追加别格列修复。

### 5.2 池规范化

- 列内容身份：`(instance_hash, date, sorted_unique_store_ids)`；来源身份另行记录。
- 相同日店集先归并再做共同排序，避免重复调用路线求解器。保留该档位下最低重算成本的已知合法排序，合并全部 provenance。
- 路线必须无重复门店且精确覆盖该店集；排序输入规范化，同成本路线按固定规则取舍。
- 不同店集不能以“去重”名义按便宜程度只留前 K 个；如需截断，作为显式搜索配置另测，记录损失与覆盖影响。
- “保留一条”不等于“该路线已证最优”；求解状态独立保存。
- 该规范化适用于评估边界，不擅自改变引擎内部定价列的数学含义或证明链。

### 5.3 路线档位的边界

A 主剖面固定共同 CP-SAT 排序规则及单路线限额，按实际状态评价。R2 作为日历生成器时关闭其内部终局精排，避免适配器再次排序导致重复开销。搜索期估计器与 B&P 内部定价属于引擎配置，单独披露，不能伪装为共同路线成本。

B 使用预先冻结的相同日店集，首批取原计划日店集；扩展采样必须记录来源并对所有路线算法一致。B 不运行日历搜索和 SP，不因路线算法不同而改变店集。

## 6. 预算、重复与运行清单

### 6.1 两种预算剖面不混称

| 剖面 | 固定方式 | 可作出的结论 |
|---|---|---|
| 机制剖面 | 每算法固定自身迭代、代数、CG轮数、节点数等工作量；记录耗时 | 增加该算法工作量带来什么收益；不宣称各算法等算力 |
| 资源剖面 | 同硬件/线程配额下固定端到端时间预算；明确阶段分配 | 同资源限制下的质量与成功率 |

预算清单必须写出具体值，不能只写“快档/标准档”。R2 可用 25K/100K/360K 迭代作为候选机制档；其他算法的实际参数与阈值在实施清单中冻结。数值未确定的格标为未排期，不进入批跑。

资源剖面覆盖初始化、搜索、规范化、路线排序、SP、验证；阶段不得透支剩余额度。冷缓存作为默认性能口径；复用缓存的另报暖缓存结果。公共输入读取与预生成矩阵成本单列。

### 6.2 组合增量的对照

对同一实例与 R2 输入，同时保留：

1. R2 使用预算 b1 的结果；
2. R2 使用总预算 b1+b2 的独立结果；
3. B&P 使用总预算 b1+b2 的独立结果；
4. R2(b1)→B&P(b2) 的组合结果。

共同评估阶段的预算计入总资源且规则一致。第1项衡量追加 BP 的收益，第2、3项判断相同总资源下组合是否值得。组合端到端成本包括父 R2 成本，即使实验调度复用了父产物也不能漏算。

### 6.3 随机重复与复现

分开 `seed_values`、`seed_count`、`replicate_id`。首轮探索可单次冒烟，正式随机算法比较使用预先冻结的多个独立重复。多 seed 合池是另一个明确配置，其方差来自多次独立 seed 组，而不是同池内四个 seed 的离散程度。

确定性验证档固定排序、种子、依赖、worker 及停止规则；比较规范化业务结果，不含耗时/时间戳。实际性能档允许限时并行求解，报告重复间差异，不承诺整条流水线逐位一致。

### 6.4 运行清单

每项包含：`run_id, experiment(A/B/C), instance_id, engine_id, route_policy, budget_profile, numeric_budgets, seed_values, replicate_id, dependency_run_ids, environment_hash`。

批跑前校验缺项、重复 run、越权依赖及预算。运行次数从清单计算，先测小批阶段耗时再估算总时长，不沿用未经验证的“两个通宵”。

## 7. 实例层与实施顺序

### 7.1 首期：真实静态实例

使用现有10条真实线、2026年7月23个工作日、已验证合同与容量走廊、固定路网矩阵。每个实例记录基线合法性与矩阵哈希。先小样本跑通 A/B/C，再扩至全部真实线。

### 7.2 扩展：受控静态实例

受控维度包括全月独立门店数 `n_stores ∈ {20,50,100,200}`、空间分布 clustered/random、周访与双周合同混合比。`daily_n` 分布另记，不能用全月200店推断单日TSP有200点。地理范围/面积与点分布分开描述，以区分密度和聚集形态。

生成器须交付：路网来源、坐标索引、非对称距离矩阵、合同及奇偶相位、日期集、容量走廊、合法初始计划、实例种子与版本。抽样组合、各组合重复数和留出集由清单冻结。数学用微型人工矩阵只用于正确性测试，不进入真实路网业务降幅。

动态插单率0%/5%/15%保留为后续方向；在定义事件时刻、冻结已执行部分及动态约束之前，不作为本版矩阵的场景轴。

## 8. 统一记分卡与证书附加项

### 8.1 所有引擎的共同字段

| 类别 | 字段/解释 |
|---|---|
| 身份 | run/config/input/code/dependency hashes，脏工作区标记，父运行 |
| 合规 | 日期完整、无重复店、合同、派生次数、R2′、容量逐项结果 |
| 质量 | native 与 pipeline 重算 km、参照状态、vs_base_pct、换星期几店数 |
| 成本 | 初始化/搜索/规范化/路线/SP/验证耗时、端到端时间、预算使用量 |
| 池 | 原始列数、独立日店集数、过滤数、来源分布、SP选列来源 |
| 状态 | 引擎停止原因、各求解器原始状态、是否有合法可行解 |

方差、可行率、证完率、耗时分位数属于跨重复聚合表。无合法解时 km/改善率为空，不用0或基线代填。超时且有合法解可同时记录 TIME_LIMIT 与 feasible=true；受限池 INFEASIBLE 不等于业务实例不可行；UNKNOWN、ERROR、UNAVAILABLE 分别保留。

### 8.2 证书字段：有资格才填写

所有算法均可报告真实业务质量；B&P 等额外报告证明能力。字段分开：

- `rmp_lp_value`：某个明确池与成本版本的受限主问题数值及 LP 状态。
- `pool_gap_pct`：同一池、同一目标下，合法上界与有效池内下界的差距。
- `certified_global_lb`、`global_gap_pct`：仅在完整问题的有效下界证明成立时填写，否则 null。
- `proof_status`、定价覆盖/收敛状态、未决节点与证明范围。

最小化问题采用 `100*(UB-LB)/abs(UB)`；UB=LB=0 时 gap=0，其他 UB=0 情况标为不适用；数值异常不得静默截成0。SP整数化目标与距离重算分开记录，不能跨单位或跨目标拼 gap。

无负列候选不等于已证明不存在负列；证书由实际数学覆盖和求解凭证决定，不由算法名称或是否使用 ESPPRC 决定。引擎内部路线成本和终局重排不同，必须验证证书是否仍适用；共同 SP 的池内最优也不能升级为全局日历最优。

## 9. 测试守卫

| 守卫 | 必须覆盖的情况 |
|---|---|
| 来源隔离 | 独立同内容列通过；隐式读取其他格产物失败；组合格依赖必须登记 |
| 池规范化 | 幂等、输入顺序无关、最低已知合法成本保留、来源合并、不同店集不误删 |
| 固定对照 | B各行消费同一店集；A各行使用同一约束和共同评价配置 |
| 成本完整 | 禁止隐藏终局精排；组合计入父成本；阶段计时无重复计费 |
| 合规与状态 | 非法日历不报告有效改善；超时可行与已证不可行正确区分 |
| 证明诚实 | 遗漏低成本列、未证完定价、受限池不可行的反例不得产生假全局证书 |
| 真值与复现 | 微型全列枚举独立真值；固定配置复现业务结果；性能档保留波动 |
| 配置完整 | 参数、版本、随机重复和运行依赖齐全后才能启动正式批次 |

测试通过表示协议得到实现；实验结果是否支持场景结论仍需独立验证。

## 10. 报告与适用域

报告按 A/B/C 分开，以实例切片展示质量—时间关系、合规率及附加证明能力。原始直接解与统一流水线结果不能混列比较；预算不同时显式标注。

组合报告同时给出相对父R2的增量和等总资源对照。新增列数、被选率为诊断，不能单独证明因果贡献，同值解可能改变被选来源。

真实与受控实例分别报告。路由规则先写成有适用范围的假设，冻结后在留出实例上验证；验证通过才回填算法指南。不因旧保底矩阵中某行≈基线就取消该机制的干净对照。

## 11. 替代方案与边界（Alternatives Considered）

| 方案 | 本版取舍 |
|---|---|
| 所有算法×所有TSP一次全展开 | 暂不采用；先解耦A/B，再少量验证交互，减少混淆与成本 |
| 所有格合池并加基线安全网 | 保留给生产协议；独立研究格不采用 |
| 不同类别只用不同指标、禁止共同质量比较 | 不采用；共同业务指标＋按资格附加的证书更清晰 |
| 仅观察引擎经过SP的最终值 | 不足以归因；同时保留native与pipeline |
| 强制各引擎同迭代数 | 不采用；不同机制的一次迭代成本不同，分机制档与资源档 |

## 12. 与现有实现的关系

现有 `contract_matrix_cell/v2` 保留生产快筛语义，新 runner 使用 `research_matrix/v1`，不回填旧数据。

估计器下沉可作为公共组件重用工作，但不能单独证明格间独立。实施前优先完成：输入/运行清单、独立引擎适配器、评估池规范化、共同评价与状态字段。B&P证明链完善与更多算法优化单独排期；未具备证书条件的运行仍可参加合法质量比较。

当前版本锁定、池剪枝等工程缺口由实施计划逐项处理。不得把设计中的期望字段或守卫写成当前实现已支持。文档命名保留兼容路径；对外采用本版的机制名称。
