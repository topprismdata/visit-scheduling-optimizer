# SVDE 认知与系统根因分析报告 (RCA)
**事件:** 为什么在首次分析销售代表【仁军】6月份业务时遗漏了严重的“频次未履约与大店脱访”问题？
**性质:** 深度认知复盘与系统能力归因（Root Cause Analysis）
**调查结论:** **本体设计具备概念表达力，但分析认知陷入了“幸存者偏差（总量幻觉）”，且本体层缺少显式的“履约偏差审计算子（Audit Operator）”。**

---

## 一、是本体设计（Ontology Design）的问题吗？

### 结论：本体具备核心概念，但在“执行审计”视角存在工具化断层

我们在 A03 v1.0.1 和本体权威库中，其实早就严密定义了相关概念：
- **`FrequencySpec`**: 定义了单周期必须拜访的频次；
- **`CadenceSpec`**: 定义了周期跨度与前后拜访间隔下限/上限；
- **`FulfillmentClass`**: 定义了 `REQUIRED`（硬履约）与 `OPTIONAL`；
- **`LifecycleState.MISSED`**: 定义了由于未履约导致的“失访状态”。

#### 本体视角的盲区（The Ontology-Tooling Gap）：
尽管这些概念存在，但在此前所有设计和测试中（包括 Scenario A/C/D/E/B），我们把 `CadenceSpec` 主要当成了 **“未来计划生成的输入约束（Input Constraint for Planning）”**，而**没有将其显式定义为一个闭环的“实际执行差异审计算子（Actual Execution Audit Operator）”**。
- 换句话说：本体知道“应该去 4 次”，但没有显式规定：**只要拿到一份实际执行表，第一步必须强行跑 `Audit(Planned Cadence vs Actual History)`**。

---

## 二、真正的根本原因：决策代理的“两大认知陷阱”

### 陷阱 1：幸存者偏差与总量幻觉（Survivor Bias & Aggregate Illusion）
这是传统数据分析师和普通 AI 最容易犯的致命错误：
- 当拿到仁军 6 月份的记录时，我的代码写的是：
  ```python
  renjun_june_rows = [r for r in data if r['门店负责人'] == '仁军' and '-06-' in r['拜访日期']]
  ```
- 这个过滤逻辑的致命漏洞在于：**它只抓取了“仁军去过的 71 条记录”，自动过滤掉了“仁军管辖、但 6 月份一次都没去过的 4 家门店”！**
- 随后的所有分析（在店时长 60.2 分钟、陈列达成率 116%、区县分布）全部是在这 71 条“已经发生的幸存数据”上计算的均值。
- **结果**: 一边是均值极其漂亮（日均 3.9 家、陈列 116%），另一边却是 4 家店彻底脱访、核心 Key 店 `NT23人民中路店` 整月被抛弃！

### 陷阱 2：退化成了传统 CRM 报表思维，而非 SVDE 决策引擎思维
- **传统 CRM 思维**: “仁军这个月打了 71 次卡，出了 18 天勤，干得不错，给他算提成。”
- **SVDE 决策引擎思维**: 
  1. 仁军管辖的 36 家门店，合同履约率是多少？
  2. 有没有 `REQUIRED` 级别的核心大店被违规 `MISSED`（失访）？
  3. 有没有低产值门店被违规 `Over-serviced`（超频占用产能）？

我在第一轮分析时，潜意识里顺着数据去统计“他做了什么”，而没有以世界模型的契约为主线去质问“**他有哪些该做而没做（Contract Violations）**”。

---

## 三、系统性改进与固化措施（Systemic Remediation）

为了确保未来任何场景下绝不再犯同类错误，我们在 SVDE 中固化以下硬性铁律：

```
┌────────────────────────────────────────────────────────────────────────┐
│               SVDE 实际执行分析与诊断不可逆审计铁律 (Iron Rule)          │
├────────────────────────────────────────────────────────────────────────┤
│ 铁律 1: 必须以【管辖客户全集 (Customer Universe)】为底表，严禁仅以【发生表】为底表 │
│         • 必须用 OwnershipPolicy 中的全量门店做 LEFT JOIN 实际执行记录  │
│         • 零拜访门店 (Zero-visited) 自动列为最高级别审计异动！          │
│                                                                        │
│ 铁律 2: 任何实际执行分析，第一步强制执行【频次履约率审计 (Cadence Audit)】 │
│         • 输出四分格：达标 (Exact) / 欠访 (Under) / 脱访 (Zero) / 过频 (Over) │
│         • 未经 Cadence Audit 严禁输出工时与路线分析！                  │
│                                                                        │
│ 铁律 3: 建立 Key 级门店脱访红线阻断机制 (Hard Guard on Strategic Stores)│
│         • Key/REQUIRED 门店只要月频次 < 规定频次，直接触发【履约事故报警】│
└────────────────────────────────────────────────────────────────────────┘
```
